# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"CCA – Customer Contact API": a prototype REST API built with Symfony 8.1, API Platform 5.0 (`api-platform/core ^5.0`), Doctrine ORM 3 (DBAL 4, DoctrineBundle 3), MySQL 8 and PHPUnit 12. There is no frontend and no login; authentication is token-only.

## Goals and conventions

- **Goal:** upgrade to Symfony 8.1 and API Platform 5, then add Messenger with RabbitMQ, voters and a CI pipeline.
- **Upgrade path:** API Platform 4.4 requires Symfony `^7.4 || ^8.0` (checked with `composer why-not`), so the order is: Symfony 7.0 → 7.4 (done), then API Platform 3.2 → 4.4 (done, including the filters: `Customer` now uses `QueryParameter` with `PartialSearchFilter`, `ExactFilter` and `SortFilter` instead of the deprecated `#[ApiFilter]`, `SearchFilter` and `OrderFilter`), then API Platform 4.4 → 5.0 (done: validation type errors now return `422` `ConstraintViolation` instead of `400`; tests use `ApiPlatform\Test\ApiTestCase`), then PHPUnit 12 and the Doctrine/Monolog bundles (still on Symfony 7.4), then Symfony 8.1 (done). The characterization tests for the `Customer` filters and ordering (`CustomerFilterTest`) stayed green when the filters were replaced; keep them green.
- **Design decisions** (all done except the anonymisation):
  - Country → City and City → Address: no cascade delete (done). The DB foreign keys have no `ON DELETE CASCADE`. Final decision (04.11.2026): Country and City are never deleted, so they have no `Delete` operation (`DELETE` answers `405`; `CityTest` and `CountryTest` pin it). Before, a parent with children was refused with `409` by a `RestrictedDeleteProcessor` (removed); before that, deleting a Country removed its Cities and Addresses.
  - Customer: never hard-delete (traceability, analysis). Soft delete is done (`deletedAt`, see Architecture); anonymisation on request (GDPR right to erasure) is still open, and the unique `email` of a deleted customer stays taken until then.
  - Keep cascade only where the child is part of the parent: `User` → `ApiToken`.
- **Authentication:** custom `ApiTokenAuthenticator` with the `x-api-key` request header. Swagger UI has an Authorize field for it (`api_platform.swagger.api_keys`); the README gives the public demo token of the admin fixture user.
- **Schema changes** only via Doctrine migrations.
- **Configuration:** prefer PHP attributes over YAML.

## Setup and commands

The app runs in Docker (`Dockerfile`, `compose.yaml`: FrankenPHP + PHP 8.4 with `ext-amqp`, MySQL 8.0.36, RabbitMQ 4 with management UI on http://localhost:15672 (guest/guest), a `worker` service that runs `messenger:consume async`, a one-off `init` service that runs `composer install`, the migrations and `doctrine:fixtures:load` on every `docker compose up` (it replaces all rows of the dev DB; `web` and `worker` wait for it), project name `cca`); the host has PHP 7.4, so run all commands with `docker compose exec web ...`. Web: http://localhost:8080, MySQL on the host: `127.0.0.1:3307`. `.env` and `.env.test` are committed with safe defaults only (secrets go to `.env.local`, which is ignored). In test, Doctrine appends `_test` to the DB name (`config/packages/doctrine.yaml`); the `cca` DB user may use all `cca%` databases (`docker/mysql/init.sql`). `composer recipes:update <package>` needs git (installed in the image) and a clean git index, so commit after each recipe; keep project-specific config (`app_user_provider`, `request_log`, MySQL `DATABASE_URL`) when a recipe conflicts. `config/reference.php` is generated by Symfony in debug mode and is committed; PHPStan skips it.

```bash
docker compose up -d --build                                # API docs: http://localhost:8080/api
docker compose exec web composer install
docker compose exec web php bin/console doctrine:migrations:migrate -n           # dev DB
docker compose exec web php bin/console --env=test doctrine:database:create
docker compose exec web php bin/console --env=test doctrine:migrations:migrate -n  # test DB (repeat after every new migration)
docker compose exec web php bin/console doctrine:schema:validate               # entities and migrated schema must match (also run in CI)

docker compose exec web php bin/phpunit                     # all tests
docker compose exec web php bin/phpunit tests/CityTest.php  # one file
docker compose exec web php bin/phpunit --filter testCreateCitySuccess  # one test
docker compose exec web vendor/bin/phpstan analyse --memory-limit=1G  # level 6, config phpstan.dist.neon (128M is too little)
```

`phpunit.xml.dist` sets `failOnDeprecation="true"` and `<source ignoreIndirectDeprecations="true">` (with `src` and `tests` as first-party code): a deprecation triggered by our code (self) or by our call of a deprecated vendor method or property (direct) fails the run; indirect ones from `vendor/` are ignored. `<deprecationTrigger>` (`trigger_deprecation()` and Doctrine's `Deprecation::trigger()`) is required: without it a deprecated vendor call is not reported at all (checked with a throwaway test). Known gaps (same test): extending a vendor class marked `@final` and loading a deprecated vendor class are classified as indirect and do not fail the run. `symfony/phpunit-bridge` was removed: it made no difference to the result of these checks. Code style: PHP CS Fixer with `@Symfony` (`.php-cs-fixer.dist.php`; `yoda_style` is switched off on purpose); check with `docker compose exec web vendor/bin/php-cs-fixer fix --dry-run --diff`, fix by running it without `--dry-run`. CI: `.github/workflows/ci.yml` (PHP CS Fixer, PHPStan, migrations, PHPUnit).

## Architecture

- **Resources:** `Customer` and `Address` are exposed through DTO resources, `src/ApiResource/CustomerResource.php` and `AddressResource.php` (`#[ApiResource]` with `stateOptions: new Options(entityClass: ...)`); the Doctrine entities only store data. `symfony/object-mapper` (8.1) maps in both directions: `#[Map(target: Entity::class)]` for DTO → entity, `#[Map(source: Entity::class)]` for entity → DTO (without it the mapper finds no target for nested objects). API Platform's own Doctrine providers still read the entities, so the query extensions and the `QueryParameter` filters work unchanged. `createdAt`/`updatedAt` are only mapped entity → DTO (`SourceClass` condition); the nested `address` list uses one `MapCollection(targetClass: ...)` per direction (without a target class the mapper reports an ambiguous mapping). Validation constraints and the serialization groups live on the DTOs (`UniqueEntity` with `entityClass` and `identifierFieldNames: ['id']`, so a `PUT` with the unchanged email is accepted). `Country`, `City`, `User` and `ApiToken` are still entities with `#[ApiResource]` (no controllers; the custom state processors in `src/State/` are `CustomerCreatedProcessor` and `SoftDeleteProcessor`; `symfony/object-mapper` 8.1 is not part of the Symfony 8.0 exam).
- **Domain model:** `Country` 1–n `City` 1–n `Address` n–1 `Customer`; `User` 1–n `ApiToken`. Country and City have no `DELETE` operation. `City::$country` has `#[Assert\NotNull]` with the message "A city without a country cannot be created" (without it a missing country answered `500` with the raw SQL message). `Customer` persists Addresses via `cascade: ['persist']`; the API accepts nested addresses only in `POST /api/customers` (see under soft delete). Serialization uses `<entity>:read` / `<entity>:write` groups (attributes from `Symfony\Component\Serializer\Attribute`; the `Annotation` aliases were removed in Symfony 8).
- **Access control** lives in `#[ApiResource(security: ...)]`: `ROLE_USER` for customers, addresses, cities, countries; `ROLE_ADMIN` for `users` and `api_tokens`. `access_control` in `security.yaml` is empty.
- **Authentication:** `src/Security/ApiTokenAuthenticator.php` is the `custom_authenticator` of the `main` firewall. It reads the `x-api-key` header, looks up the user via `UserRepository::findByApiToken()` (→ `ApiTokenRepository`), and returns a `SelfValidatingPassport`. Failure returns a JSON 401. Tokens are created with `php bin/console app:api-token:create <email>` (`src/Command/CreateApiTokenCommand.php`): it stores a random token for an existing user and prints it once. Only the SHA-256 hash of a token is stored (`api_token.token_hash`, `ApiToken::hash()`; a token is random and 120 characters long, so a fast hash is enough). `/api/api_tokens` can only list, get and delete (admin) and never shows a token or a hash; the migration `Version20261104100000` hashed the existing plain text tokens (it cannot be reversed). The tests send the plain demo tokens from `UserFixtures::tokenFor()`.
- **API Platform config** (`config/packages/api_platform.yaml`): only JSON-LD (`application/ld+json`); PATCH needs `application/merge-patch+json`. `standard_put: false`, `serializer.hydra_prefix: true` (API Platform 4+ turns the `hydra:` prefix off by default; it is kept for existing clients). `keep_legacy_inflector` and `event_listeners_backward_compatibility_layer` were removed in 4.x. `PUT` is not a default operation in API Platform 4, so `City`, `Country` and `Customer` list their operations explicitly (like `Address`).
- **Customer filters** are `QueryParameter`s on the `GetCollection` operation of `CustomerResource` (only there, so Swagger shows them only for `GET /api/customers`; the property paths refer to the entity): `name` and `email` use `PartialSearchFilter` (case-insensitive by default: `LOWER(field) LIKE LOWER(:value)`), `address.city.name` uses `ExactFilter`, `order[name]` uses `SortFilter` (`properties: ['name']`; other fields are ignored). `ExactFilter` has no case option, so the case-insensitive city search depends on the MySQL collation; `CustomerFilterTest` pins it.
- **Request logging:** `src/EventListener/LogRequestAndResponseEventListener.php` listens to `kernel.terminate` and logs to the `request_log` Monolog channel (tagged in `config/services.yaml`). The handler exists only in `when@dev` and writes to `var/log/request/`.
- **Timestamps:** `Customer` sets `createdAt`/`updatedAt` with `#[ORM\HasLifecycleCallbacks]` (`Country`, `City`, `Address`, `User` do the same). Gedmo and the Stof bundle were tried and dropped: the soft delete works with them (checked on ORM 3 with a throwaway script), but they would be a dependency for one feature.
- **Customer soft delete:** `DELETE /api/customers/{id}` runs `src/State/SoftDeleteProcessor.php`, which only sets `deletedAt` (admin only, via the `CUSTOMER_DELETE` voter; its subject is the `CustomerResource`). `src/Doctrine/ExcludeDeletedCustomersExtension.php` (an API Platform query extension) hides deleted customers from the list and from item requests (`404`). The row and its addresses stay; `ExcludeDeletedCustomersExtension` also hides the addresses of a deleted customer (inner join on `customer`, `deletedAt IS NULL`; list and item answer `404`), while the rows stay in the database. Addresses in `POST /api/customers`: `CustomerResource::$address` is in the group `customer:create`, which only the `Post` operation denormalizes (`PUT`/`PATCH` use `customer:write`, so they ignore it). The mapping DTO → entity for `address` has the condition `App\ObjectMapper\CustomerIsNew` (target has no id): API Platform maps `PUT`/`PATCH` onto the stored entity (`ObjectMapperInputProcessor`, `mapped_data`), and a replace would delete addresses through `orphanRemoval`. `Customer::setAddress()` only adds, because `EnglishInflector::singularize('address')` returns `addres`, so `PropertyAccessor` finds no adder and would otherwise skip the property without an error (checked 04.11.2026 with a throwaway script). Open: what `PUT`/`PATCH` should do with a list of addresses (replace or add). Addresses of an existing customer are changed through `/api/addresses`.

- **Messenger:** `POST /api/customers` runs `src/State/CustomerCreatedProcessor.php`, which lets API Platform's persist processor save the customer and then dispatches `App\Message\CustomerCreated`. The message is routed with `#[AsMessage('async')]` to the `async` transport (RabbitMQ, `MESSENGER_TRANSPORT_DSN` in `.env`); `CustomerCreatedHandler` only writes a log line. In `test` the transport is `in-memory://` (`config/packages/messenger.yaml`), so tests and CI need no RabbitMQ (CI still needs the `amqp` PHP extension because `symfony/amqp-messenger` requires it). No failure transport yet.

## Tests

- Functional API tests in `tests/` (`CityTest`, `CountryTest`, `CustomerTest`, `CustomerFilterTest`, `UserTest`) extend API Platform's `ApiTestCase` and need a real MySQL test database.
- Each test loads fixtures with Liip `DatabaseToolCollection` (`UserFixtures`, `CountryFixtures`, `CityFixtures`, `CustomerFixtures` in `src/DataFixtures/`; fake data only); the tables are emptied before each load. `config/packages/liip_test_fixtures.yaml` sets `keep_database_and_schema: true`: the tests run against the migrated schema (the default would drop and rebuild the schema from the entities on every load, which hid migration errors and took about two minutes). Because the purge is a `DELETE`, auto increment ids are not reset: tests find ids by name with `App\Tests\Support\FindsFixtureIds`. The test DB must be migrated before the first run. DAMA was removed (it conflicts with Liip's schema handling and would add little).
- `UserFixtures` creates `test@example.com` (`ROLE_USER`) and `admin@example.com` (`ROLE_ADMIN`), each with a fixed API token; tests read it back and send it as `x-api-key`. `CreateApiTokenCommandTest` tests the token command with `CommandTester`; `ApiTokenTest` pins the hashing and the `api_tokens` resource; `CustomerResourceTest` pins the DTO behaviour. `CustomerVoter` has no unit test; `CustomerTest` checks it through the API (`403` for a normal user, soft delete for an admin).
- Tests assert Hydra keys (`hydra:member`, `hydra:totalItems`, `hydra:Error`) and the media type `application/ld+json` (API Platform 4 sends no `charset`). The keys depend on `serializer.hydra_prefix: true`; check them again when upgrading API Platform.
- Test classes set `protected static ?bool $alwaysBootKernel = true;` (API Platform stops booting the kernel by default).
